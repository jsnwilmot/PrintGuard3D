# Controlled recommendations compatibility design

Design recorded before implementation, 2026-10-29. Authority: #23 and the bounded owner policy in #14. Base: d03eb59cb887cfad335241b9f56d260b5a75abdc. Independent Architect review remains required.

- Keep all accepted profile JSON bytes and stored source enums unchanged. Derive Manufacturer Documented only from the existing exact-definition/model verifier, scoped to the published fact. Pending Verification remains visibly pending. General recommendations are never promoted to documented.
- Add optional strictly validated `recommendation` decision metadata to newly accepted reminder tasks, new completion snapshots and new observation task snapshots. Version 1 records the immutable initial owner decision, exact model, group/boundary, approved/default versus owner interval, source, policy revision, acknowledgment date and usage basis. Source text and warnings come from an application policy allowlist, not arbitrary imported claims. No historic metadata is backfilled.
- Keep Dexie 2/native IndexedDB 20 and all existing stores/indexes. No migration or record transformation. The initial empty-v30 fence proposal was experimentally disproved (see correction below) and removed before submission. Old strict backup parsers fail closed; an already-running old executable is a separate unresolved coexistence/rollback limitation, not something a version number can retroactively prevent.
- Keep backup schemaVersion 1 and add optional `recommendationPolicy: {version:1}` whenever decision metadata occurs (including historical observations/logs). Existing readers use strict schemas and reject the unknown marker/nested fields before writes. New readers accept old backups unchanged, require the marker for new metadata, validate all model/source/decision invariants, and preserve immutable merge conflicts. No lossy legacy export. Backups do not manufacture local disclaimer consent.
- Retain report schema version 1 because columns/rows are already extensible: append visible recommendation context columns without moving old column positions; copy provenance/caveats into all formats. Report JSON is an output, not a backup/import interface. ICS descriptions and schedule printing carry the same caveats. Historical views use captured metadata only, never current printer/rule substitutions.
- Create separate inspection/review reminders only, never edit a manufacturer servicing rule. Exactly 5 fan hours -> 6 months; exactly 10 -> 3 months; exactly 5 X/Y -> 1 month; exactly 5 Z -> 3 months. No near-boundary rounding. Restrict these to exact Creator 5 FDM/FFF; Pro receives no series transfer. Pro may create an owner-defined condition-only filter inspection with no default cadence. No cleaning, lubrication, tension or replacement procedure is attached.
- Require explicit review and acknowledgment at the mutation boundary. Reject/defer writes nothing; custom months are User Defined. Existing reminder provenance is immutable; later custom edits retain the initial decision but display User Defined and cannot acquire manufacturer status or move to another model.
- Optional 30-calendar-day printing average requires 31 distinct daily endpoint readings covering the complete window through today, monotone counters, no conflicting same-day endpoints, finite physically possible daily deltas <=24 hours, and an explicit printing-counter declaration. Missing days remain unknown (never inferred idle). Date-only readings use calendar date arithmetic, not local DST elapsed hours. This is PrintGuard's convention, with fan working/printing mismatch disclosed. A manually reported boundary is explicitly an owner assertion, not a measured manufacturer fact.
- Preserve perpetual recurrence beyond 2500, legal wording, local acknowledgment, observation immutability, ownership, custom schedules and manufacturer verification checks. No production database, hosted app, deployment, merge or release acceptance is authorized.

Validation will retain 195 regressions, 45 original acceptance assertions and 92 browser/print cases. Original migration/version assertions remain unchanged; prospective whole-profile badge assertions change to the limited documented-facts label while raw source assertions remain intact. No acceptance requirement is suppressed. Add focused policy, import, consent, history, averaging, variant, offline and accessibility tests. F07 remains PARTIAL; #14 and #22 remain open.

## Corrected compatibility decision after experimental validation

The initially proposed native-v30 fence was **disproved**, not implemented as a guarantee: installed Dexie 4 retries a VersionError without an explicit version and accepts the newer layout. An empty version increase cannot protect legacy runtime access. Final design retains Dexie 2/native 20, with no stores/indexes or data migration. Version-specific original tests stay unchanged. New decision fields remain optional strict record-format extensions; old strict backup readers reject the policy marker and nested fields before writes. New readers reject unsupported policy metadata. A dedicated regression records the actual old-Dexie fallback and checks raw records retain General Recommendation, the full disclosure in description and decision metadata.

An already-running old executable cannot be retroactively made metadata-aware. Do not present database versioning as that guarantee. Existing fields (title, General Recommendation source, description and safety) carry readable caveats even to old code, but an old completion implementation will not capture the new structured history field. **Legacy runtime coexistence/rollback is an unresolved deployment limitation for independent Architect review (#16)**: keep the current version, obtain a pre-feature backup and isolate any rollback; do not remove metadata to force old imports. This branch does not authorize deployment. Avoid a destructive store rename, duplicate user database or artificial source-enum change to simulate protection.
