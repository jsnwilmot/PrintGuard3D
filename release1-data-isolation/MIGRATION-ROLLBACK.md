# Proposed migration, divergence and rollback protocol

Design-only, 2026-10-31 UTC, Issue #34, approved main **90461bd1f07e0c3fa5ad2807438c920fb3d48a40**. Symbols/options are defined in [DESIGN.md](DESIGN.md). **No migration, source read, database creation, schema/backup change or deployment was performed.** This is a protocol for a separately authorized implementation, not executable instructions for an existing private workshop.

## Ownership and invariants

The workshop user controls source selection, current-device v1.0 acknowledgment, migration permission, backup custody, comparison review and destination adoption. The product owner controls deployment/market decisions; that role does not authorize silently reading another person's browser. A future source adapter gets read-only access to the explicitly selected `S` in that profile. Only a future destination importer writes `D`. Source records, source consent, caches and recovery copies are never deleted, renamed or modified by migration. No old-source write is necessary to indicate cutover.

The current supported data contract is seven core stores (`printers`, `tasks`, `logs`, `readings`, `inventory`, `repairs`, `profiles`), `preferences` and optional captured `observations`. Identity, graph consistency, photos, current source/decision semantics and immutable historical facts all matter. Unclassified historical category/currency/provenance stays unclassified. Imported observations retain captured model/task/state/time/zone/offset and must never be recomputed using present printers. Profiles stay pinned to immutable versions; custom rules, usage and perpetual baselines are not reset.

## Supported input / no-migration assessment

| User/data situation | Proposed safe behavior |
| --- | --- |
| Future new user, no source data requested | Create governed `D` only after required acknowledgment; start an empty workshop. No source search, copy or history inference; no migration receipt pretending data was transferred |
| User has only a valid historical schema-1 file, including legitimate legacy missing fields | Strict current-reader validation and explicit file-scoped preview; preserve exactly the recorded facts and unknowns. State that recovery covers this file, not unrecorded work. No automatic enriched history or observed points |
| Same-origin source is available and representable by the reviewed reader | Permission-gated consistent read-only snapshot, verified new-reader full backup, validation/restore rehearsal, digest comparison and staged cutover below |
| Old source-only user has no verified file but wants to keep it | May remain on source; no automatic migration or compatibility certification. A separately approved read-only recovery reader is needed to obtain a supported backup. Never advise using an old-code export merely because download succeeds |
| File is an enriched old-code export rejected by supported validation | Preserve original bytes/checksum and error; block import. Do not strip fields, add a guessed policy marker, invent decisions or call it repaired by re-export |
| Source contains incomplete stale-created history, unknown stores/unsupported schema, invalid graph or contradictory observations | Preserve source and an explicitly labelled forensic snapshot if safely readable; default STOP on migration. Recovery may not be possible from available facts. Separate reviewed recovery/exception policy required |
| Source unavailable, storage cleared or no usable backup | No promise of recovery; do not create/delete a source to make a wizard appear successful. User may choose a separately acknowledged empty new workshop, with loss/unknown state explicit |
| Destination already used | Never replace silently. Same imported snapshot is recognized; new conflicting data goes through strict reviewed reconciliation, not a reset/re-copy |

Schema validity alone cannot prove complete provenance. A fresh reader can serialize a policy marker while a log written by stale code still lacks its decision. Without a known prior snapshot, legitimate legacy omissions and later losses may be indistinguishable. Display that uncertainty; never infer a log's missing decision from its current task. Default block an identified incomplete post-baseline record. Any owner policy permitting as-recorded uncertain legacy history must be separately reviewed and cannot certify it complete or manufacturer-verified.

## Phase protocol and commit points

| Phase/state | Allowed operations | Completion / failure behavior |
| --- | --- | --- |
| P0 — UNINITIALIZED | Public help/data handling and minimal destination control/acknowledgment UI; no workshop/source queries | New namespace literal/build capability must be known. No fallback to `S` when `D` is missing or broken |
| P1 — CONSENTED / PREFLIGHT | Explicit fresh v1.0 acknowledgment in destination, separate migration permission, source/file selection and capacity check | Source/file acknowledgment is not copied as device consent. Cancel leaves source unchanged; no user-record import |
| P2 — SNAPSHOT_VALIDATED | Short read-only source snapshot or selected file; strict validation; backup export/restore proof; complete diff preview | Unknown/unrepresentable input stops. Snapshot/file evidence retained. No normal destination writes/background observations |
| P3 — IMPORTING | One destination-only transaction writes validated payload, preserved current acknowledgment and operational receipt state VERIFY_REQUIRED | Any abort rolls back the transaction. Do not publish READY, active pointer or notifications early |
| P4 — VERIFY_REQUIRED | Fresh connection reads committed data, verifies all per-record/store digests and independent recovery copy; source recheck | Mismatch remains locked/recoverable, never auto-falls back to source. A retry must identify what was committed |
| P5 — RECONCILE_REQUIRED or READY | Source comparison and explicit user cutover confirmation; READY only for a matching approved generation | Source divergence blocks ordinary migration completion. Final state/epoch/receipt changes are destination-local and conditional on unchanged generation |
| P6 — MONITORED / REVIEW_REQUIRED | Normal compatible destination operations; permission-based source rechecks on later opens/manual request | Late source changes flagged, preserved and reconciled. No claim that old tabs were technically frozen |

State names are proposed semantics, not new enums or tables already added. A dedicated strict control record/store and exact schema/export treatment require approval before implementation. Receipt concept: format version, migration ID, source identity/context label, source/file digest, original/expected/observed store counts and digests, destination namespace family, generation/capability, state, validation/build identity, acknowledged cutover time and last source-check disposition. No original log/observation acquires a fabricated migration/acknowledgment field. Avoid collecting browser fingerprint identifiers or host secrets.

### P1/P2: source collection and verified backup

For A, use a pure read-only adapter rather than booting the current `App`/global `db`. Open only named `S` without requesting a version. Abort any creation/upgrade event; close on versionchange, blocked access or error, report source unavailable and leave it untouched. Use a single read-only transaction covering all present supported source stores to copy a consistent set into memory; a supported legacy source without an observations store contributes no observations, while missing required stores stop the read. Wait for transaction completion. Compute hashes/validate/export afterward, not via unrelated asynchronous work inside a live IDB transaction. Enumerate store names to detect unknown content; do not silently omit it or claim a complete recovery file. Record actual database version, declared reader/build capability and adapter result without treating the number as a writer fence.

The supported reader must apply existing strict backup/graph/image/profile/observation/decision rules and supported extensions. Preserve input bytes and a raw canonical snapshot separately from validated/normalized values. A safe current-format backup from source must include all representable rows, `recommendationPolicy` where required, the complete versioned overdue history and preferences. It must be parsed and restored by the supported reader in a disposable isolated validation destination, then read back and compared. A successful download, checksum alone, filename, export timestamp or old app's approval is insufficient.

For B, `O2` does not query the old origin's IndexedDB. Obtain the file through a separately reviewed read-only recovery reader at `O` (or an approved equivalent preserving that origin's storage access), then user-controlled transfer. Serving a reader at `file://` or a new path/origin does not grant access to `O` storage. Delivery of that reader at a live old origin needs separate hosting authorization; it must have no normal app bootstrap/observer/writer. Old SW fallback to an old app is not the recovery reader: verify expected build/capability before source access and require strict destination validation. No CORS/proxy/postMessage auto-transfer workaround, embedded bridge, provider connection or deployment is authorized in this design.

Keep two independent complete copies when practical, with user-selected custody; files are not encrypted by the app. Confirm storage headroom for source + destination + memory/files/control records. Do not delete source/caches to make room. Browser persistence/estimates are best-effort and not backup guarantees; insufficient space stops before writes.

### P3/P4: destination atomicity and record comparisons

There is **no source+destination distributed transaction**. After snapshot, source writers can resume. Atomicity claimed here is only the destination import and its control state, using the complete destination store scope. During P3/P4 no profiles/defaults, readings, logs, preference saves or observation callbacks may run outside that restricted operation. Preserve the current destination's explicit acknowledgment while importing other preferences; do not import source/file consent. Current replacement's deliberate renewal semantics remain for ordinary restore; migration cannot silently make a different rule without approved tests.

Canonical comparison proposal v1: table/key sorted by a specified binary ordering; recursively sort object keys; preserve array order, stored text/code points, all numeric values and image bytes. Use complete records and record IDs, not just counts or visible fields. Keep raw exported-file SHA-256 separately from canonical digests. Define the same JSON data semantics as supported backups: absent and explicitly undefined **schema-optional** properties may compare equivalent, and numeric -0 may compare as 0; list these technical equivalences in the receipt. They do not permit dropping any defined recommendation, unknown field, array entry or user text. NaN/infinity, undefined required values and other unsupported non-JSON content stop instead of being coerced. Exact algorithm/version/test vectors must be fixed in implementation review; do not assume a hash authenticates the source or reveals omitted real-world work.

Maintain three comparison layers: original source snapshot `B`; explicit expected target `E` after approved validation; actual destination `D`. Counts and per-ID/value digests for every core store and observations must match `E`; no unexplained losses/additions. Compare preferences field by field: fresh destination acknowledgment is an explicit permitted difference; source lastBackup must not be advanced by read-only export. Import clock/receipt/build metadata is separate, not a changed historical fact. Only permitted active trust quarantine differences may enter `E`, listed individually before consent. Never change IDs/owners/intervals/usage baselines, accepted immutable definition bodies or historical logs/observations to make hashes match. If required normalization exceeds reviewed rules, stop.

After commit, reopen and read all destination rows. Export a complete supported destination backup, validate and restore it in a separate disposable destination and compare again. The proposed receipt sidecar preserves migration evidence separately from the existing data envelope; losing it does not invalidate workshop data but does remove cutover certainty. A fresh restore must validate data and establish a new local control/acknowledgment decision, never trust imported READY/epoch/consent. Exact control metadata and sidecar schema remain unapproved.

On repetition, identical migration ID + source/file digest + completed receipt identifies the prior transfer; no duplicate rows or replay of older mutable values. A changed source or a destination already changed by real work is a new reconciliation, not a replace. Multiple participating new tabs coordinate generation checks and one importer; locks assist but destination transaction checks decide. Refusal/cancel/abort changes no user records. Destination setup may have created an empty locked DB/control/ack record; disclose that limited effect rather than claiming absolutely no local writes.

## Source freeze limits and late-write reconciliation

The new reader being read-only does **not** make `S` read-only for other executables. Ask the user to stop work, export/verify, close identified old tabs/windows and installed apps, and inventory other clients in this same browser profile. Client lists/messages do not prove there are no sleeping/BFCache/restored/uncooperative writers. The source read transaction only gives a consistent snapshot during that read.

Capture `B` before import and `L` after destination verification. If different, enter RECONCILE_REQUIRED; do not show a lossless completed cutover. After resolving any valid changes, take another source snapshot immediately before the user confirms cutover. Equal digests establish equality only at those checkpoints, not a future guarantee. Define an owner-approved quiet-window/check cadence before implementation; no arbitrary delay establishes a safety proof.

| Three-way comparison (`B` baseline, `L` late source, `D` destination) | Default disposition |
| --- | --- |
| `L == B` | No observed source divergence; allow reviewed cutover with residual late-write risk stated |
| New uniquely identified source records | Validate full graph, duplicate activity, chronology and provenance; preview proposed additions. No auto-import. Missing post-baseline decision metadata blocks lossless reconciliation |
| Same historical/profile/observation ID with different facts | Preserve `B`, `L`, `D` and backups; immutable conflict STOP. No overwriting or current-state reconstruction |
| Mutable source and destination edits differ | No timestamp/last-writer-wins selection; explicit per-record reviewed resolution, monotone usage and ownership validation. Separate authorization if current workflows cannot represent it |
| Source deletion | Never cascade-delete destination. Show difference and retain evidence; no inference that the user intended destination deletion |
| Source inaccessible / comparison unavailable | UNKNOWN, not unchanged. Keep destination isolated and readable only under the approved recovery policy; do not claim synchronized or lossless cutover |

Default proposed refusal policy: before initial READY, changed/unavailable required source evidence stops completion. After READY, a detected divergence or a failed required source check moves participating destination writers to REVIEW_REQUIRED/read-only; validated data and exports remain available, with no silent source fallback. The owner must decide review cadence and any separately approved detached-source operating policy; absence of a new check is not proof of no late writes. Clean new users with no migration source do not acquire a fictitious source-monitoring requirement.

After READY, late source work remains possible. For A, on later explicit source-check permission/open, compare to the saved baseline and flag changes; do not constantly scan arbitrary profiles. For B, only a newly obtained supported source file/reader report can extend that evidence. Destination writes remain isolated; unresolved source changes must be prominently reviewable. If actual write-free migration is required, external user/IT quiescence control or a new-origin operating boundary must be established and tested; this design cannot enforce it on old code. No source deletion or automatic reconciliation is the default remedy.

## Failure and rollback rules

| Failure | Proposed recovery |
| --- | --- |
| Cancel before import / consent declined | Source unchanged; no copied user records. Public help and empty-new-workshop path remain available |
| Quota/error/tab collision during destination transaction | Abort all payload/control changes for that transaction. Preserve source and validated file; retry only after identifying committed state and revalidating generation/input |
| Power/process loss before commit | Treat transaction outcome as unknown until reopening/receipt+data verification; never infer commit from UI progress |
| Commit succeeded, readback/backup verification interrupted | Stay VERIFY_REQUIRED. Reopen and compare complete committed payload; do not recopy over it blindly or activate background recording |
| Offline/network loss during first-use/update | If complete compatible cached assets/reader/backup are absent, stop safely. No mixed-build fallback to source writes or “download again online” promise after data loss |
| Repeated import or restore | Strict identity/immutable conflict rules and retained observations; no deletion of captured history through legacy replacement or duplicate samples |
| Rollback requested after cutover | First retain and verify complete new destination backup plus receipt sidecar. Use an old pre-upgrade backup only in a **fresh separate old-version profile/origin/database**; never point old code at `D`, rename `D` to `S`, downgrade it in place or strip fields |

Rollback restores only the older snapshot; it omits later decisions/observations/work not contained there. Retain the upgraded destination and complete new backup. If no valid old snapshot exists, old-version rollback may be unavailable; prefer a reviewed forward recovery. Reusing an old origin with the wrong SW/binary or treating a new metadata file as old consent is not an acceptable rollback. Human custody, actual installed PWA/OS behavior and host cache controls remain unverified under #15/#25/#16.
