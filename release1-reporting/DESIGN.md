# Reporting/history design preflight — written before schema implementation

Authorization: owner-approved [decision #13](https://github.com/jsnwilmot/PrintGuard3D/issues/13#issuecomment-6471768461), implementation [#18](https://github.com/jsnwilmot/PrintGuard3D/issues/18). Base main: `988d7d837849fc7acb9babf90bab4ea579a19a77`. This is an engineering design for review, not release approval or permission to access production data.

## Observation contract

- Add one `observations` table in **Dexie version 2 / native IndexedDB version 20**, retaining the exact original eight store definitions (seven workshop tables plus preferences). Upgrade only creates an empty store and indexes; it does not read, clear, enrich or rewrite existing rows or generate history.
- Recording starts only when the owner selects **Start recording observed history** after current disclaimer acknowledgment and actual local data loading. A new optional `preferences.observationRecording` flag defaults to absent/off. Once started, capture current committed states on app open, relevant persisted task/printer changes and an observed date/timezone change while the app is open. The existing open-app clock may notice a date change; there is no background collector or claim about closed-app execution. Pausing recording preserves observations and scheduling.
- Each immutable record belongs to one captured printer, grouped with other printers by a collection batch ID. It contains exact UTC `observedAt`, captured local date, IANA timezone/UTC offset, event source, recorded printer name/manufacturer/model/technology/profile version/archive state and actual cumulative readings. Task facts include stable owner/task IDs, title/category/priority, active rule baseline/interval/postponement/condition/enabled state, recorded source/version, computed status, eligibility and overdue count. Do not capture notes, photos, serials, locations, personal/device identifiers or expense data.
- Capture all printer/task coverage, including archived/disabled exclusions; count overdue only for enabled rules on active printers. Verify status/count consistency using **captured facts only**, never current rules when displaying/importing history. Every plotted point drills to those frozen task facts, even after edits, archive or deletion. Per-printer series avoid inventing workshop totals from partial/uneven coverage.
- Collect under one read/write transaction spanning preferences, printers, tasks and observations. Recheck current acknowledgment and recording flag, read actual committed state, compute a single timestamp, compare the latest captured facts per printer and append only changed facts or the first actual observation of a UTC day. StrictMode, reloads and identical visits do not duplicate points. A→B→A changes remain meaningful observations. No startup backfill, retrospective samples or inferred closed-app periods.
- Bound records to 20,000 total, 96 per printer/UTC day, 1,000 printers and 10,000 covered tasks per capture. On capacity failure stop adding samples and show a persistent explanation; keep all existing history. No automatic pruning/retention expiry. Maintenance schedules remain perpetual and independent of observation capacity. Gaps and all unobserved instants are explicitly unknown; points are not joined into an assumed continuous history.

## Backup evolution, conflict and rollback boundaries

- Preserve root backup envelope `schemaVersion: 1` and its existing unsupported-future-schema rejection. Add an **optional, strictly versioned `overdueHistory: {version: 1, records: [...]}` extension**. Empty, unactivated legacy-compatible exports omit it. This preserves the original schema-2 rejection contracts while giving the new data its own explicit version. Original/Phase 1–5 strict readers reject the extension/new recording preference; there is no silent field stripping or downgrade claim.
- Full backups include all observations, including deleted-printer history. Individual-printer backups include only that printer's immutable observations; no other printer identity/rows are disclosed. Self-contained captured ownership permits deleted live entities; tasks within an observation must belong to its captured printer. Reject duplicate IDs/content, invalid counts/status/UTC-local dates, unknown extension versions and conflicts with an existing immutable observation, including during replacement.
- Observations are **append-only across all imports**, including full core replacement. A legacy file has no observation data to replace; existing observations remain. A newer file merges immutable records idempotently. The restore preview explicitly explains this scope and reports observation conflicts. Core replacement retains its existing explicit warning and renews acknowledgment. All eight workshop/preference stores and observation additions share one transaction; any write/quota failure rolls back clears and writes. No observation is overwritten or silently discarded by an older backup.
- Upgrade failure aborts the native version-change transaction, preserving the original version-1 database. After a successful upgrade, an explicitly versioned native v10 open fails closed with a version error. Dexie 4 has an automatic schema-discovery fallback: an old application can reopen a newer database without requesting a lower native version, so old-binary in-place operation is unsupported and must never be used as a rollback; do not force a destructive database downgrade. Verified operational rollback uses the pre-upgrade backup in a **fresh isolated old-version database**, leaving the upgraded database and complete new backup intact. New observations/newer fields require the newer reader. Reopen the new version to recover all data; no promise that older software can consume unknown history.
- The legacy synthetic review harness will initialize the additive empty current store before baseline comparisons and open the current version read-only thereafter. Existing 151/45/20/45 assertions remain unchanged. New tests independently build a genuine native version-10 database, exercise actual upgrade/abort/downgrade boundaries, and inspect the new table; the harness adaptation is not upgrade evidence or a weakening of old data assertions.

## Shared report and chart contract

One typed selector produces report columns, typed values, row identities, captured attribution, selected printer/task context, statistics and deliberate unclassified separation. Screen, CSV, JSON, HTML and print consume the same selected result. Drilldown queries carry exact record IDs plus date/printer/manufacturer/category/priority/status/currency/coverage context. No current-rule reconstruction of missing log metadata.

Six focused visualizations satisfy seven approved subjects: recorded monthly completions covers completion trend and tasks completed per month; monthly recorded compliance; activity per printer; upcoming workload; separate-currency expenses; observed overdue points. Every point/bar has a pointer action and a directly associated keyboard record control. Compliance excludes postponements and shows unknown without eligible records. Workload uses one next confirmed dated occurrence per rule, separately identifying due/overdue, undated reached usage thresholds and non-due estimates; estimates never become due dates or historical observations.

Standalone HTML uses only escaped selected result data, fixed embedded CSS and validated local raster images. No scripts, SVG, imported CSS, external resources, analytics, forms or fetches; restrictive meta CSP adds defense in depth. HTTP(S) documentation hyperlinks are escaped, never executable user HTML. Wide schedules use printable record details rather than compressed columns. JSON reports have their own `kind`, `reportSchemaVersion`, generated instant, exact filters, typed columns/rows/provenance and safety caveats; they are distinct from backups. Unclassified records require separately labelled explicit exports and are absent from main outputs.

External legal/manufacturer/manual/device/hosting gates remain open. No merge, deployment, production migration, access change, unrelated phase or Release 1 approval is authorized.
