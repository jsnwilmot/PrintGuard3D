# Phase A design and compatibility boundary

Recorded before implementation, 2026-10-30. Authority: #26; approved main f18f4adfa31723c5af8e8e10f7099e32c6252dd1. Branch release1/safety-brand-transparency.

Use a versioned, data-only safety reference policy, separate from immutable manufacturer profiles. Match only existing exact-model/source/version definitions through the current full `isVerifiedTask` verifier. Reviewed source identities are data, not inferred keywords or priority. Each mapping can identify multiple hazard references; neither an empty mapping nor an unknown procedure means safe. Separate procedure-specific facts from general model notices, and keep unreviewed powered-work/service sequences explicit. Technician advice is application advice consistent with the existing disclaimer, not an invented manufacturer-only restriction.

No database, task, log, observation, profile or backup fields change. The extra completion acknowledgment is a transient UI review gate plus a submit check, not a stored attestation, hardware interlock, qualification certificate or claim that review happened before past work. Existing general review remains. Completed physical/unassessed work requires context review; skipped work uses a clear non-performance confirmation and no hazardous-work acknowledgment. Review-only suggestions remain distinct. Reset context acknowledgment when outcome/date changes. Retrospective copy says reviewed now for this record. Offline/flagged documentation does not prevent truthful recording after the user reviews available context; missing safety evidence is never certified.

Current task explanations/exports can show the current policy context. Historical source/status/snapshots stay byte-identical and are never assigned a new past hazard/acknowledgment. Generic export safety explains that unidentified hazards are not proof of safety; current schedules may include sourced hazard context. No duplicate generic disclaimer, new consent version or renewal. `src/legal.ts` text/version remains unchanged.

Existing API helpers retain their compatibility contract; the new gate applies to the first-party completion form, like the existing general checkbox. Direct legacy programmatic callers and cached Dexie clients are not retroactively fenced. This UI control is not an enforceable hardware/security boundary or auditable proof of acknowledgment. #16 remains open. A persistent hazard/acknowledgment schema would need separate reviewed compatibility design and authorization; none is introduced here.

Phase B is explicitly waiting for the owner-authorized Phase A merge, per the owner's response on 2026-10-30. No Phase B branch, privacy notice or market/legal assessment is implemented in this PR. Its later source work must coordinate Help/Settings/footer changes against approved merged Phase A.
