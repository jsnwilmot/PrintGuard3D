# Reviewed profile authoring and updates

Profiles are strict data in `src/profile-library/<manufacturer>/<model>-<version>.json`, discovered by Vite without changing the scheduling engine. `src/profile-manifest.json` inventories every released identity/version, LF-normalized UTF-8 byte digest, source-authority hosts, review date and legacy exception. `scripts/validate-profiles.mjs`, invoked by repository validation in CI, detects missing entries, duplicate identities, modified content and incomplete provenance. Digests detect accidental change; they are not manufacturer signatures or independent proof of review.

## Adding a manufacturer or model

1. Audit exact-model official sources. Record URLs, accessibility, source revision/date, applicability, documented trigger, materials, precautions and remaining uncertainty in the documentation register. Distinguish recurring, condition, corrective and unavailable content. Read video content before treating indexed video titles as evidence of steps or cadence.
2. Add a strict profile JSON and manifest entry. Each exact variant needs a distinct stable profile ID; require model, manufacturer and technology equality. Include source-host authorities as reviewed data in the manifest. No scheduler/provider adapter is required for supported trigger types. Unsupported trigger semantics require separate design, not a fabricated conversion.
3. Give every new template a permanent `templateId`, matching `profileId` and `profileVersion`. Keep IDs across renames. Add `legacyTitles` only for confirmed old-title mappings; duplicate/ambiguous mappings are blocked rather than guessed. Never repurpose an ID for a different procedure.
4. Use `recurring` only for confirmed periodic requirements. Published usage bands are `usage-dependent`, with an inactive condition base and exact `intervalOptions`; owner selection creates a verified rule only when its entire definition matches the reviewed option. Corrective and nonrecurring condition references belong in `references`, outside automatic task templates. Unverified sources remain pending.
5. Add coverage notes and exact-model references. Missing or unreviewed documentation is visible. App-reviewed verification means the application's evidence has been reviewed against a specific source snapshot; it is not manufacturer endorsement, current safety assurance or complete-model certification.
6. Run schema/domain/UI/native regressions, the unchanged acceptance suite, TypeScript, static validation and production build. Submit source evidence and the complete old/new comparison in a draft PR for human review. Only an approved source change adds to the runtime allowlist; importing JSON or checking an acknowledgment never does.

## Publishing a later definition

Never edit a released JSON body or reuse an existing version. Add a higher semantic version and new manifest digest, retaining all prior files. The existing Creator 5 v1.0.0 file is the unchanged accepted Phase 1 body; its legacy identity exception must not be copied to new definitions. Versions use SemVer ordering; malformed install versions, downgrades, equal-precedence aliases and same-version body changes are rejected. Legacy non-SemVer backups remain readable, but installation over a non-SemVer registry needs separately reviewed handling and is intentionally fail-closed.

`profileChanges.ts` compares all properties, additions/removals, keyed task/reference changes, ordering and applicability. Review in Settings before acceptance; deferring writes nothing. Target selection excludes incompatible printers. Changing a target/procedure/band clears acknowledgment. A selected usage-dependent procedure without a band cannot be accepted for a printer. Stale registry previews and ambiguous identities are rejected transactionally.

Applying an update archives immutable definitions and adds only selected **new** procedures to the chosen printer using its current readings and today's baseline. Existing rules—including changed defaults—remain unchanged and pinned, with the original intervals, customizations and service baseline. Historical logs/readings, ownership and other printers are untouched. Removed templates do not delete active rules. Updating the printer's profile version is distinct from each existing rule's version. Adopting a changed existing rule requires a separate explicit owner edit; Phase 3 does not implement automatic field merging or batch replacement.

Definitions live in the existing IndexedDB profiles store under `version:<encoded-profile-id>:<encoded-version>`. New registrations retain their exact applied definition; updates retain prior/current/applied reviewed versions. The database layout/version stays unchanged. Schema-1 backups retain these definitions and optional profile/reference/usage-band/source-flag metadata. Phase 3 reads legacy schema-1 exports; **earlier strict readers may reject enriched Phase 3 exports**. This is forward-reader compatibility, not downgrade compatibility. Do not open an enriched database in an old build or treat a rollback as data migration.

Manual source flags are local preferences, not remote reports or an automated validator. Preserve them in backups, review current official instructions when flagged, and introduce a new source-reviewed version when corrections are established. Do not alter historical service facts to repair documentation.
